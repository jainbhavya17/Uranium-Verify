1. Executive summary, boundaries and assumptions
URANIUM VERIFY is a human-controlled preliminary scrutiny and regulatory decision-support layer for AICTE 
approval workflows. Institutions identify an applicable application category, review existing authorized 
institutional history, supply forms and supporting evidence, receive permissible pre-submission deficiency 
guidance and submit a case. AICTE personnel receive a separate protected workspace to review document 
extraction, cross-record consistency, issuer responses, infrastructure evidence, regulatory checks, provenance 
signals and traceable reports.
1.1 Scope and goals

Cover all 14 agreed feature groups within the prototype through functional vertical slices or clearly 
identified limited-scope demonstrations.

Preserve authorized institute history by academic year, application type, programme and approved intake; 
never overwrite an approved snapshot with a pending request.

Implement institutional document-upload constraints before expensive extraction; distinguish readable, 
marginal-quality, unsupported, infected/suspicious and manually reviewable files.

Allow only authorized AICTE roles to view internal risk prioritization, forensic analysis, private source 
responses and review actions.

Expose evidence-backed findings referencing the exact document/page/field or trusted data source, and the 
applicable rule version.

Keep source-adapter interfaces replaceable: mock registry now; approved issuing-authority/AICTE systems 
in production.

2.2 Information separation

Institution sees readiness, completeness, expiry, factual mismatches, rectification requests, official status 
and its own prior approved history. It does not see internal fraud heuristics, undisclosed model scores, 
officer private notes or other institutions.

Officer sees full authorized case evidence, source responses, confidence/limitations, regulatory clauses, risk 
reasons and review controls.

Specialist sees only routed verification tasks; supervisor sees assigned operational oversight; platform 
admin sees rule/connector administration rather than unbounded document contents.

Shared account pages (notifications and settings) use the signed-in role and tenant scope; notifications are 
not an alternative authorization channel.

3.3 URL and navigation contracts

A route requires an authenticated principal unless it is Home, Login or Password Recovery. Invalid access 
returns a safe 403/404 state without leaking case existence.

Each application has a stable opaque ID; URLs contain opaque identifiers, never certificate data or personal 
information.

Use a consistent case breadcrumb: Applications > {Application ID} > {Section}; on mobile use a compact 
back link plus section selector.

Navigation disabled pending sufficient permissions, but backend always independently re-checks RBAC, 
institutional membership and case assignment.
4. UI design system, accessibility and responsive behavior
Design objective: a calm, precise public-administration SaaS interface. Treat data credibility as more important 
than decorative effects. The interface must work for low-bandwidth users, keyboard-only users and officers 
handling dense evidence.
DESIGN AREA
REQUIRED SPECIFICATION
Color and tone
Deep navy for headers/text; muted teal as primary interactive 
accent; slate neutrals and white surfaces. Semantic colors 
reserved for errors, warnings, success and pending status. 
Never rely on color alone.

4.2 UX behavior rules

Each user-facing action has an explicit pending/success/failure state. No fake successes for asynchronous 
OCR or source confirmation.

Persist uploaded-file progress separately from extraction status; enable draft autosave and recovery after 
refresh.

Do not block an institution solely because an AI model detects possible image manipulation; route that 
concern to authorized review.

Use terms: Draft, Submitted, Under Preliminary Review, Clarification Requested, Pending Source 
Verification, Referred for Inspection, Review Completed; do not label automated output Approved/Rejected.

Support a reduced-motion setting, native form autocomplete where safe, proper focus trapping in dialogs, 
and screen-reader status updates.

9. End-to-end user journeys and state transitions
9.1 Institution: registration to application submission
1.
User visits S01 > S02, authenticates; backend resolves identity, institution membership and permissions; 
role directs to I01.
2.
I01 surfaces previous approved history and unfinished drafts; I02 opens own cases, I03 selects academic 
year and application type from approved catalog.
3.
Backend snapshots current approved institutional record and starts draft; I04 prefills historical data, 
distinguishes previously approved vs currently proposed changes.
4.
I05 calls requirements evaluator to generate applicability-aware checklist by year, category, programme 
and stage. Not-due and conditional requirements are explicitly marked.
5.
I06 uploads each supported document; client screens format/size and gives readability hints, then backend 
validates actual bytes, scans and processes the file before accepting.
6.
Processing worker extracts text (direct PDF or OCR), classifies document, extracts fields, records 
confidence/uncertainty, source page and content hash.
7.
I07 runs institution-safe completeness, validity and consistency checks. User re-uploads corrected 
documents or edits draft where permitted.
8.
I08 displays full application review; server recalculates submission gate from latest revision and current 
rule version, obtains declaration, freezes submission version and writes audit event.
9.
I09 shows acknowledgment and public status. If officer requests correction, user follows I12 > I13 and 
submits new versions without overwriting original evidence.
9.2 AICTE: receipt to reviewed findings
10. Submission event creates/updates a scoped queue item and kicks off full evaluation. O01/O02 show 
workload but do not imply that the case is already verified.
11. Officer O03 inspects application identity, proposed changes versus historical approved state and results 
from individual services.
12. O04 examines source documents, machine-extracted fields, cross-document discrepancies and Evidence 
Graph edges.
13. O05 inspects authorized issuer/API/QR/digital signature results, visual anomaly findings and separated 
C2PA/SynthID provenance signals.
14. O06 reviews applicable version-controlled APH rules, RAG-supported citations and deterministic 
compliance outcomes. Low confidence becomes insufficient evidence, not fabricated compliance.
15. O07 reviews room-wise records and infrastructure claims, optionally creating a targeted 
specialist/inspection task.
16. O08 records a human-authored observation, routes to a specialist/supervisor, requests clarification or 
finalizes a review-stage recommendation (not automatic regulatory approval).
17. Verification specialists use O09; generated, versioned reports become available in O10; notifications update 
the institution only when a review action is explicitly publishable.

11.2 Exact validation stages
18. Frontend preflight: accept-list, byte size, file count, image dimensions, filename and obvious format 
warnings. Show per-file error before network transfer.
19. Transport: authorized pre-signed upload or protected API, streamed upload and progress; cap request size 
and enforce tenant/application ownership.
20. Backend sniff: inspect actual MIME/file signature, extension consistency, decompression limits, PDF 
trailer/readability and safe parser policies.
21. Threat screening: malware scanning and quarantine, PDF JavaScript/embedded risky content restrictions, 
rate limits and anti-zip-bomb memory ceilings.
22. Readability: document opens, page count within policy, text layer availability, scan clarity/contrast, 
orientation and OCR quality. Give reupload advice for recoverable deficiencies.
23. Normalize: route born-digital pages to text extraction; scans to OCR; retain original orientation, page 
coordinates and checksum.
24. Extract/classify: type-specific schema, typed fields, confidence/uncertainty and source box; never fabricate 
absent fields.
25. Post-extraction validation: compare against checklist, application and history; create findings; enqueue 
source verification where appropriate.
26. Persist: attach full processing state, worker version, timestamps, original document ID, derived artifact IDs 
and audit event. Notify authorized uploader when action is required.

11.4 PDF/image quality algorithm
Use inexpensive deterministic checks first. For digital PDFs, inspect parseability, text presence, page dimensions 
and extracted spans. For image scans, inspect size, orientation, contrast, blur indicators, OCR token count and 
the completeness of fields expected for its category. Combine these into a user-friendly quality state (GOOD / 
MARGINAL / UNREADABLE) while preserving individual check outputs. Thresholds are tunable developer 
heuristics; only objective security and technical hard limits should cause automatic upload rejection. A forged-
looking but technically readable document is not rejected on upload; it is held for officer-side forensics.

13.2 Regulation-aware RAG design
37. Administrator registers authoritative APH, circular or FAQ with source URL, checksum, 
publication/effective dates, academic years and categories; ingestion cannot publish a rule.
38. Parser extracts section hierarchy and page references; creates chunks with clause, section, page, 
source_version, applicable_year and source_approval flags.

matching filter semantics.
40. For a case, filter by academic year, category, effective interval, approval state and access scope before 
hybrid keyword/semantic ranking.

matches and actual extracted evidence; show no answer if grounding is weak.
42. Rule evaluation remains separate: a deterministic evaluator consumes approved rule IDs, not 
conversational LLM output.
43. Officer can inspect original excerpt and rule mapping; no citation-free "compliant" declaration.
13.3 AI image / certificate provenance
C2PA validates available signed provenance assertions for compatible media; SynthID indicates a supported 
watermark detectable by a provider tool. Their availability depends on provider and file transformations. 
OpenAI documents content provenance checks for supported image/audio files; the tool does not generalize to 
every AI system. These are not substitutes for issuer verification, and a result of not_detected does not prove 
human origin. The viewer shall show provider, check type, checked file version, status and verification 
timestamp independently.

m2 for a division of 60. If application declares 75 m2 and certified room schedule records 58 m2, system creates 
(a) declared-versus-certified area mismatch and (b) possible area deficiency of 8 m2 under that selected rule. It 
attaches room ID, certified plan page and exact APH clause. Do not apply this rule to unrelated programmes or 
statuses; verify exemptions and effective rule version first. Figures are illustrative test data from the earlier 
blueprint, not observed institution data.

16.1 Threats and defenses

Cross-tenant IDOR: institute A requests institute B application ID; backend returns 
forbidden/indistinguishable response and audit event.

Malicious PDF: content sniffing, anti-malware scanning, sandboxed parsers, resource caps and no shell 
execution on attacker-controlled filenames.

Prompt injection in uploaded PDF or retrieved handbook text: documents are data; restrict tools and 
allowed outputs, cite original sources and never run instructions contained in documents.

Forged certificate: compare claims with authorized issuing sources and signing trust anchors; do not 
confuse visual similarity with source confirmation.

Admin rule tampering: version immutable published rules, require source documentation, approval 
workflow and reproducible tests.

Privilege escalation: revoke sessions and enforce assignment-level checks; data filtering must occur at 
query layer as well as UI.
